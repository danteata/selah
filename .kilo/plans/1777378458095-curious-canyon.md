# Plan: Improve Semantic Verse Detection for Short/Partial ASR Quotes

## Problem

When a preacher says "Wisdom has built her house" (Proverbs 9:1), the semantic detector fails because:

1. **Short fragment vs full verse**: The ASR fragment (26 chars, 5 words) is compared against the full KJV verse ("Wisdom hath builded her house, she hath hewn out her seven pillars" — ~70 chars). The embedding similarity is ~0.3-0.4, below any reasonable threshold.

2. **ASR corruption dilutes the signal**: Multiple ASR variants ("The system has built a house", "Wisdom has built a hair house") get embedded separately. Wrong ones compete with the correct one.

3. **No query-length-aware thresholding**: The sermon listener uses a flat threshold (0.45) regardless of query length. The UI search hook has `calculateDynamicThreshold` but the sermon listener doesn't use it.

4. **Lowering the threshold globally creates false positives**: A flat 0.45 threshold would match unrelated passages that share common words.

## Root Cause

**Asymmetry between query and document granularity**: Each verse is embedded as one monolithic vector; the query may be a 5-word partial quote. `all-MiniLM-L6-v2` produces a single vector optimized for document-level similarity — a short fragment simply can't match a full verse reliably.

## Architecture Changes

### 1. Shared Retrieval Policy (`src/lib/semanticRetrievalPolicy.ts`)

Create a single source of truth for threshold, normalization, and validation — used by both sermon listener and UI search hook.

**Exports:**

```
getDynamicThreshold(wordCount: number): number
  1-4 words  → 0.38
  5-8 words  → 0.44
  9-14 words → 0.49
  15+ words  → 0.52
  Configurable floor/ceiling constants at top of file.

removeStopWords(text: string): string
  Inline stop word list (~80 common English + archaic stop words: "hath", "doth", "shalt", etc.)
  Returns text with stop words removed, preserving order.

normalizeQuery(text: string): string
  Lowercase, strip punctuation, collapse whitespace, remove stop words.
  Returns normalized string for lexical comparison.

validateSemanticMatch(query: string, verseText: string, wordCount: number): boolean
  1. Extract content words from query (normalize + remove stop words)
  2. Extract content words from verse text (same pipeline)
  3. Best-effort stem mapping: built~builded~build, hath~has, doth~does, etc.
     (~30 common archaic↔modern pairs, not a full stemmer)
  4. Check overlap:
     - Queries ≤5 words: require ≥1 content-word overlap
     - Queries >5 words: require ≥2 content-word overlaps, or 1 rare-term overlap
  5. Return false if overlap requirement not met → candidate is discarded
```

### 2. Dynamic Threshold in Sermon Listener

Port `getDynamicThreshold` into `SemanticVerseDetector.performSegmentedSearch`:
- Compute threshold **per sentence** based on word count
- Replace the static `this.config.threshold` with the dynamic threshold
- This allows short fragments to match at 0.38 while long reliable text requires 0.52

**In `useSemanticVerseSearch.ts`:** Remove the local `calculateDynamicThreshold`, import the shared `getDynamicThreshold` instead.

### 3. Progressive Enrichment (Controlled Retries)

Replace the current `enrichShortSentences` (which always prepends context) with a progressive retry strategy:

```
for each short sentence (<9 words):
  Attempt A: sentence alone → search → validate
  Attempt B: previous_sentence + " " + sentence → search → validate
  Attempt C: sentence + " " + next_sentence → search → validate
  Stop on first validated hit. Max 2 retries per sentence.
```

**Why this matters:** "Wisdom has built her house" alone might match Proverbs 9:1 via a fragment embedding. Prepending irrelevant context ("She has hearing her seven children. Wisdom has built her house") can actually *reduce* similarity because the embedding shifts toward the wrong content.

### 4. Multi-Fragment Verse Embeddings (Index-Time)

Replace the single-embedding-per-verse with multiple fragment embeddings.

**Fragment extraction (`src/lib/extractVerseFragments.ts`):**

```
extractVerseFragments(verseText: string): Array<{text: string, type: "full" | "clause" | "window"}>
  1. "full" — the complete verse text (always included)
  2. Clause chunks — split on [,:;.!?], trim, keep clauses with 4-14 words
  3. Window chunks — sliding windows of 6-8 words, stride 3, over the first 16-20 words
  4. Deduplicate near-identical fragments (char similarity > 0.7)
  5. Cap total fragments per verse: max 4-6 (to control cost)
  6. Minimum 4 words per fragment (shorter is noise)
```

**Example for Proverbs 9:1:**
- Full: "Wisdom hath builded her house, she hath hewn out her seven pillars"
- Clause: "Wisdom hath builded her house" (6 words)
- Window stride-3 over word range: "Wisdom hath builded her house she" (6 words), "builded her house she hath hewn" (6 words), "her house she hath hewn out" (6 words)

**Schema updates (`convex/schema.ts`):**
```
verseEmbeddings table additions:
  fragmentType: v.string()      // "full" | "clause" | "window"
  fragmentIndex: v.number()     // 0 for full, 1+ for fragments
  embeddingVersion: v.string()  // "v1" for legacy, "v2_fragments" for new
```

**Search behavior update (`convex/verseEmbeddings.ts`, `localEmbeddings.ts`):**
- Retrieve top K fragment matches (K=20)
- Group by verse reference, keep best fragment hit per verse
- Return top N verses after dedup

**Seeding pipeline updates:**
- `VerseEmbeddingSeeder.tsx` and `LocalEmbeddingSync.tsx` call `extractVerseFragments` and embed each fragment
- Tag each embedding with `fragmentType`, `fragmentIndex`, `embeddingVersion = "v2_fragments"`

### 5. Versioned Migration for Re-Seeding

- New embeddings are tagged `embeddingVersion = "v2_fragments"`
- Existing v1 embeddings remain as fallback
- Query path checks for v2 availability; falls back to v1 if v2 coverage < 95%
- Admin panel shows: v2 coverage %, seeding progress, failed batches
- No data loss — v1 rows are never deleted during migration

## Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Fragment embeddings increase storage ~3-4x | Cap fragments per verse (max 5-6). ~100K-120K rows for KJV, manageable in IndexedDB and Convex |
| Re-seeding is slow | Seed in batches of 50, progress bar, resumable. Only once per version |
| Lower thresholds → more false positives | Validation guard (lexical overlap check) filters them. Stricter for longer queries (≥2 overlaps) |
| Progressive enrichment adds latency | Stop on first validated hit. Max 2 retries. Most matches succeed on attempt A or B |
| Archaic↔modern word gap hurts matching | Best-effort stem map (~30 pairs: hath~has, builded~built, etc.) in validation. Not a full stemmer, just common Bible English |
| v1/v2 migration issues | v1 always available as fallback. No v1 data deleted. Admin can monitor coverage |
