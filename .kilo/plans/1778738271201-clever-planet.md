# Selah — Spec-Driven Development Plan

## Overview

This document defines well-scoped specifications for 11 identified issues/features. Each spec follows a consistent structure: **Problem**, **Evidence**, **Acceptance Criteria**, **Approach**, and **Affected Files**. Specs are ordered by priority (user-facing impact first).

## SPEC-01: Search Response Delays (Regex + Semantic)

### Problem
Initial Bible verse search is slow because regex parsing and semantic embedding search run sequentially, with the embedder lazy-loaded on first use. Users see a blank/loading state for 1–3 seconds before results appear, even for simple reference queries (e.g., "John 3:16") that regex should resolve instantly.

### Evidence
- `BibleList.tsx:70-76` — `useSemanticVerseSearch` is initialized with `debounceMs: 400` and `minQueryLength: 3`, but the hook itself has an internal 300ms debounce (`useSemanticVerseSearch.ts:239`). **Total latency: ~700ms before semantic results appear.**
- Regex search (via `parseBibleQuery`) runs synchronously in the same render cycle as the semantic search setup, but results are not shown until the semantic search completes or times out in some code paths.
- `useSemanticVerseSearch.ts:248-250` — The embedder is initialized on first `search()` call (`if (!isEmbedderReady) { await initEmbedder() }`), adding 1–3 seconds of model loading on the very first search.
- `localEmbeddings.ts` — Prewarm cache is in-memory only, lost on page reload. No prefetching strategy.

### Acceptance Criteria
1. Regex matches (explicit verse references like "John 3:16") appear within **100ms** of typing.
2. Semantic results appear within **500ms** after the embedder is warm.
3. The embedder model is preloaded on app startup (or when Bible panel opens), not on first search.
4. A loading indicator is shown for semantic search while the embedder is initializing.
5. Regex and semantic results render independently — regex results are never blocked by semantic search state.

### Approach
1. **Preload embedder on mount**: Call `initEmbedder()` when `BibleList` mounts (currently deferred to first search). Move the preload to `useSemanticVerseSearch`'s mount effect.
2. **Split rendering**: In `BibleList`, render regex results immediately in a separate section. Don't gate regex results on `isSearching` or `hasEmbeddings`.
3. **Reduce debounce**: Lower semantic debounce from 400ms to 250ms. The internal 300ms in `useSemanticVerseSearch` should be configurable and lowered to 200ms.
4. **Prewarm strategy**: After embedder initialization, prewarm the most common version's embeddings into the in-memory cache.
5. **Progressive loading UX**: Show shimmer/skeleton for semantic results area while embedder loads.

### Affected Files
- `src/hooks/useSemanticVerseSearch.ts`
- `src/components/bible/BibleList.tsx`
- `src/services/sermon-listener/localEmbeddings.ts`
- `src/lib/semanticRetrievalPolicy.ts`

## SPEC-02: Monitor Display Detection Shows Only on Live Output Screen

### Problem
When multiple monitors are detected, the live output always opens on the same screen regardless of which monitor the user selects in `ScreenPicker`. The user's monitor choice is not respected — the live window renders on whatever display the Presentation API or Tauri defaults to.

### Evidence
- `useNativeMultiMonitor.ts:178-213` — `openLiveWindow` in web mode: if `config.monitor_id` is not `'presentation-api'`, it calls `multiMonitorService.openLiveViewOnScreen()`, but this method uses `window.open()` with screen coordinates that depend on the Screen Enumeration API (experimental, Chrome-only). Most browsers fall through to the generic `window.open()` which ignores the target screen.
- `useNativeMultiMonitor.ts:86-96` — Desktop mode correctly calls `nativeMultiMonitorService.getMonitors()` and `setMonitors()`, but the web fallback (lines 98-121) calls `detectScreens()` which returns mapped monitors but **doesn't persist the user's selection** in a way that `openLiveWindow` web path uses correctly.
- `ScreenPicker.tsx` — The `flashMonitor` function in the hook (line 262) only works in desktop mode (`isDesktop` guard). Web users cannot identify which monitor is which.

### Acceptance Criteria
1. In desktop (Tauri) mode, `moveToMonitor()` and `openLiveWindow({ monitor_id })` move the live output to the selected monitor within 2 seconds.
2. In web mode, if the Presentation API is available, the user can select from available displays and the presentation opens on the chosen display.
3. In web mode without Presentation API, a clear message explains that monitor selection requires Chrome 100+ or the desktop app.
4. The `monitors` state is always populated after `detectMonitors()` in both desktop and web modes, and `selectedMonitorId` is persisted to `localStorage` so it survives page reloads.
5. `flashMonitor()` shows a visual identifier on the selected monitor in desktop mode. In web mode, an alternative identification method is shown (e.g., colored border on the live output window).

### Approach
1. **Persist selected monitor**: Save `selectedMonitorId` to `localStorage` via `appStore`. Restore on hook initialization.
2. **Web fallback improvement**: When `openLiveWindow` is called with a `monitor_id` in web mode, compute `window.open()` coordinates from the selected monitor's `left`/`top`/`width`/`height` to position the popup on the correct screen.
3. **Flash identification in web**: Add a colored border overlay to the live output window that matches the `ScreenPicker` color for 3 seconds after opening or on demand.
4. **Fallback message**: If no screens are detected (no Presentation API, no Screen Enumeration API), show a prominent notice in `ScreenPicker` with instructions to use the desktop app for multi-monitor support.

### Affected Files
- `src/hooks/useNativeMultiMonitor.ts`
- `src/services/multi-monitor/index.ts`
- `src/components/live/ScreenPicker.tsx`
- `src/components/live/LiveOutput.tsx`
- `src/store/appStore.ts`

## SPEC-03: Collaboration Features — Contributor Issues

### Problem
Contributors in live sessions experience several issues: (1) No reconnection/recovery after network drops, leaving the session stale. (2) Queue suggestions can be silently lost if the connection drops between local add and server confirmation. (3) Collaboration mode cannot be changed after session start — requires ending and restarting. (4) No optimistic UI for contributor actions in `moderated` mode.

### Evidence
- `useLiveSession.ts:430-446` — `handleAddToQueue` adds locally first, then fires mutation. If the mutation fails, it rolls back. But if the connection drops before the mutation, `pendingQueueSlideIdsRef` accumulates items that are never retried.
- `useLiveSession.ts:424-427` — Solo/local mode adds to queue directly, but shared session checks are not re-attempted on reconnection.
- `useLiveSession.ts:307-327` — `startSession` takes `collabMode` but there's no `updateCollaborationMode` mutation.
- No reconnection logic exists anywhere in the file.

### Acceptance Criteria
1. When Convex connection drops and reconnects, the session state (queue, current slide, role) is automatically refreshed from the server within 5 seconds.
2. Pending queue additions that failed due to disconnection are retried once on reconnection.
3. The operator can change collaboration mode (Strict ↔ Moderated ↔ Open) during an active session without ending it.
4. Contributors in Moderated mode see their submitted suggestions in a "pending" state with a visual indicator (spinner/dotted border) until the server confirms acceptance.

### Approach
1. **Reconnection recovery**: Add a `useEffect` in `useLiveSession` that watches `isConvexConnected` transitions from `false` → `true`. On reconnection, refetch the session state and reconcile local state with server state.
2. **Retry queue**: Implement an offline queue in `useLiveSession` using `pendingQueueSlideIdsRef`. On reconnection, replay all pending mutations.
3. **Collaboration mode mutation**: Add a `setCollaborationMode` Convex mutation. Add a `updateCollaborationMode` callback to `useLiveSession`. Add a UI control in `LiveSessionControls` or settings to change mode (operator-only).
4. **Optimistic pending state**: In the queue UI, show pending items with a distinct visual state (dotted border + spinner). Confirm state changes to solid once server acknowledgment arrives.

### Affected Files
- `src/hooks/useLiveSession.ts`
- `src/hooks/useConvexConnection.ts` (or provider)
- `src/components/live/LiveSessionControls.tsx`
- `src/components/live/LiveOutput.tsx`
- `convex/liveSessions.ts` (new mutation)

## SPEC-04: Remove Sloppy Purple Colours

### Problem
The app's primary accent color is teal (`--accent-teal` / `primary-500`), but purple (`purple-500`, `purple-600`) is used inconsistently across 50+ locations for unrelated features (embedding sync, NDI badge, collaboration indicator, template category, schedule icon, etc.). This creates visual noise and undermines the brand identity.

### Evidence
- `grep` for `purple` across component files shows 50+ instances in at least 15 component files.
- Purple is used for embedding sync status, NDI indicator, worship template category, schedule modal, team management superadmin badge, and landing page gradients.
- The design system already defines `--accent-teal` as the primary color. Purple appears to be a legacy or inconsistent choice.

### Acceptance Criteria
1. All purple color usage in components is replaced with semantically appropriate colors:
   - **Embedding sync / Bible search**: teal accent (`primary-500/600`) or status-specific colors (amber for in-progress, emerald for complete).
   - **NDI indicator**: Use `primary-500` or a neutral status color.
   - **Worship template category**: Use a warm amber/orange (consistent with sermon template's amber) or differentiate from the primary accent with a distinct non-purple hue.
   - **Schedule modal icon**: Use `primary-500`.
   - **Superadmin badge**: Use a neutral gray/dark scheme instead of purple.
   - **Landing page gradients**: Migrate from `purple-600 → pink-600` to `primary-600 → primary-800` gradients.
2. No instances of `purple-` Tailwind classes remain in component files (exclude third-party code).
3. The visual hierarchy remains clear: primary actions use teal, status uses semantic colors (amber/blue/gray), categories use distinct warm/cool hues.

### Approach
1. **Audit**: Create a mapping of every purple instance → replacement color based on context.
2. **Category colors**: Define a consistent category palette (user confirmed amber for worship):
   - `announcement` → blue-500
   - `worship` → amber-500 (replaces purple)
   - `sermon` → orange-500
   - `prayer` → emerald-500
   - `general` → slate-500
3. **Status colors**: Use `amber` for loading/sync, `emerald` for complete, `red` for error, `teal/primary` for primary actions.
4. **Systematic replacement**: Edit each file, replacing `purple-*` classes.
5. **Verify**: Visual regression test / manual walkthrough of all affected views.

### Affected Files
- All component files in `src/components/` with `purple` classes (~15 files)
- `src/components/modals/CreateTemplateModal.tsx` (category definition)

### Problem

3. The title bar shows only session status (Live / Recording indicator, participant count) and a minimal actions dropdown, not the full collaboration mode picker.

2. **Settings UI**: Add a "Default Collaboration Mode" dropdown in `SettingsModal` under Display (or a new Live section).
3. **Refactor LiveSessionControls**: Replace the inline mode picker with a compact dropdown or popover that shows the current mode. Use `defaultCollaborationMode` from store as the default.
4. **Simplify title bar**: Move session start/join buttons to the settings or a popover. Show only status indicators in the title bar.

## SPEC-06: Theme Selection vs Custom Themes/Templates

### Problem
The app lacks a theme customization system. Users can choose background images per slide type in settings, but there's no way to create, save, or apply custom visual themes (color palette, font family, accent color, etc.). The current "templates" are per-slide background defaults, not full themes. The distinction between "theme" and "template" is unclear in the UI.

### Evidence
- `SettingsModal.tsx` — Background tab allows selecting default backgrounds per slide type, but no theme controls.
- `appStore.ts` — Settings include `slideStyle` (font, blur, brightness, etc.) but no theme palette or accent color selection.
- `CreateTemplateModal.tsx` — Templates are slide-level defaults (background + style), not app-wide themes.
- No dark mode toggle exists in settings despite `isDarkMode` being in the store.

### Acceptance Criteria
1. A **Theme** section in Settings allows selecting from preset themes (e.g., "Classic" = teal accent + serif fonts, "Modern" = teal accent + sans-serif, "Warm" = amber accent + serif).
2. Each preset theme defines: accent color, font family, border radius, and background default per slide type.
3. A **Custom Theme** builder (stretch goal for v2) allows adjusting individual properties. For v1, preset themes with manual overrides in "Display" settings is sufficient.
4. Templates remain slide-level defaults (background + layout) and are independent of themes.
5. Dark mode toggle is added to Settings → Display.

### Approach (v1 — Preset Themes + Dark Mode Toggle)
**Decision: Presets + dark mode only (no custom theme builder in v1).**

1. **Define theme presets**: Create `src/constants/themes.ts` with 3-4 preset theme objects:
   - "Classic" — teal accent, serif font, default backgrounds
   - "Modern" — teal accent, sans-serif font, clean backgrounds
   - "Warm" — amber accent, serif font, warm backgrounds
   Each preset defines: `accentColor`, `fontFamily`, `borderRadius`, `backgrounds` (per slide type).
2. **appStore**: Add `activeThemeId: string` (default: `"classic"`) and `themeOverrides: Partial<ThemeConfig>` to settings.
3. **Theme context**: Create a `ThemeProvider` that merges the active preset with overrides and applies CSS custom properties to `:root`.
4. **Settings UI**: Add a "Theme" section in `SettingsModal` with preset cards (visual preview + label).
5. **Dark mode toggle**: Add a toggle in Settings → Display that sets `isDarkMode` in `appStore` and applies/removes the `dark` class on `<html>`.

### Affected Files
- New: `src/constants/themes.ts`
- New: `src/providers/ThemeProvider.tsx`
- `src/store/appStore.ts`
- `src/components/settings/SettingsModal.tsx`

## SPEC-07: Repeat Sermon Listener Detections Don't Trigger Verse After Being Already Detected

### Problem
When the sermon listener detects a verse and the speaker repeats the same verse reference or text later, the system re-activates the verse (shows it again) but does **not** trigger the full detection pipeline (auto-lookup, auto-display, slide creation). The verse appears in the detected list but isn't displayed to the congregation.

### Evidence
- `useSermonListener.ts:1018-1034` — The `hasReActivated` branch sets `currentVerse` and calls `lookupVerse`, but the `dedupeVerses` function (referenced but not shown in the excerpt) may suppress the verse if it's already in `detectedVerses`.
- The `SemanticVerseDetector` class in `semanticVerseDetection.ts:339` uses `matchedReferences` to deduplicate within a single search, but there's no cross-search dedup tracking for re-surfacing previously detected verses.
- `useSermonListener.ts:1078` — Comment: "Re-activate if already detected, don't add duplicate to list" — this suggests re-activation is intentional but incomplete.

### Acceptance Criteria
1. When a previously detected verse is mentioned again in the sermon audio, the system re-triggers auto-lookup and auto-display (if those settings are enabled).
2. The verse is **not** duplicated in the detected verses list — it moves to the top or flashes/highlights as "re-activated".
3. A cooldown prevents rapid re-triggering (e.g., same verse within 30 seconds is ignored).
4. The UI shows a visual indicator that the verse was re-detected (e.g., a pulse animation or "↻" icon).

### Approach
1. **Re-activation tracking**: Maintain a `Map<string, number>` (reference → last activated timestamp) in `useSermonListener`. When a verse is detected, check the cooldown:
   - If within 30s cooldown → skip re-activation.
   - If past cooldown → re-trigger auto-lookup/auto-display, update timestamp.
2. **Deduplication**: The `dedupeVerses` function should return the existing verse reference (not filter it out) so the caller can decide whether to re-trigger.
3. **UI indicator**: Add a `retriggerCount` or `lastActivatedAt` field to `DetectedVerse`. In the sermon listener panel, show a subtle pulse animation on re-activated verses.

### Affected Files
- `src/hooks/useSermonListener.ts`
- `src/types/index.ts` (DetectedVerse type)
- `src/components/sermon-listener/SermonListenerPanel.tsx`

## SPEC-08: Whisper Transcription Hallucination Mitigation

### Problem
The Whisper transcription (both local Whisper.cpp and Desktop Whisper via AudioWorklet) sometimes produces hallucinated output — repetitive text, fabricated Bible references, or "Thank you" loops during silence. This leads to false verse detections and poor transcript quality.

### Evidence
- `whisperCppTranscription.ts` and `desktopWhisperTranscription.ts` — No post-processing or hallucination filtering on the raw transcript output.
- `semanticVerseDetection.ts:136-141` — `containsExplicitVerseReference()` filters some false positives, but only for regex-level detection. Semantic detection can still match on hallucinated text that resembles Bible verses.
- `useSermonListener.ts` — No minimum confidence filtering or hallucination pattern detection on incoming transcripts.
- The VAD service (`vadTranscriptionService.ts`) helps by only transcribing speech segments, but when speech is detected with low energy, Whisper can hallucinate.

### Acceptance Criteria
1. Transcripts are filtered for common Whisper hallucination patterns before verse detection runs:
   - Repetitive loops (same phrase repeated 3+ times)
   - "Thank you" / "Thanks for watching" filler patterns during silence
   - Numerically unlikely Bible references (e.g., "Chapter 999")
2. A minimum confidence threshold for semantic verse detection is enforced (already partially implemented via `getDynamicThreshold()`), but should also consider transcript segment confidence if available.
3. The sermon listener UI shows a "low confidence" indicator when detected verses may be based on uncertain transcription.
4. Desktop Whisper AudioWorklet validates audio energy before sending to Whisper, skipping near-silent chunks.

### Approach
1. **Hallucination filter**: Create `src/services/sermon-listener/hallucinationFilter.ts` with functions:
   - `isRepetitionLoop(text)`: Detect 3+ consecutive identical phrases.
   - `isFillerPattern(text)`: Match known Whisper filler patterns.
   - `filterTranscript(text)`: Apply all filters, return cleaned text or null.
2. **Integrate filter**: In `useSermonListener`, run `filterTranscript()` on each new transcript chunk before passing it to `SemanticVerseDetector.addText()`.
3. **Audio energy check**: In `desktopWhisperTranscription.ts`, compute RMS energy of the AudioWorklet buffer. Skip transcription if energy is below a threshold (configurable, default -40dB).
4. **Confidence indicator**: Add a `transcriptionConfidence` field to `DetectedVerse`. When the transcript had potential hallucinations filtered, mark the detection as "low confidence" and show a visual indicator.

### Affected Files
- New: `src/services/sermon-listener/hallucinationFilter.ts`
- `src/hooks/useSermonListener.ts`
- `src/services/sermon-listener/desktopWhisperTranscription.ts`
- `src/services/sermon-listener/whisperCppTranscription.ts`
- `src/types/index.ts`

## SPEC-09: Custom Templates Not Visible in Studio Layout

### Problem
Custom templates created via "Save as Template" or "Create Template" modal are not consistently shown in the studio layout's template selector. The studio layout uses a different template browsing mechanism than the dashboard, and custom templates may not appear or may be filtered out.

### Evidence
- `ContextPanel.tsx` — The studio layout's context panel imports `TemplateItem` but doesn't have a full template browser.
- `TemplateBrowser.tsx:28` — `useTemplates()` returns `templates` (system) and `customTemplates` (user-created), but the studio layout may only render `templates`.
- `useTemplates.ts` — `getFileUrl` always returns `null`, meaning custom template thumbnails are unresolved.

### Acceptance Criteria
1. Custom templates appear alongside system templates in the studio layout's template selector.
2. "Save as Template" from a slide creates a template that's immediately visible in the studio layout without page refresh.
3. Custom templates show a rendered preview thumbnail, not just a gradient placeholder.
4. Templates are grouped by category (announcement, worship, sermon, prayer, general) in the studio layout, with the same category colors as the main template browser.

### Approach
1. **Unify template sources**: In `ContextPanel.tsx`, merge `templates` and `customTemplates` from `useTemplates()` into a single list, or use the `TemplateBrowser` component directly.
2. **Fix `getFileUrl`**: Implement proper Convex storage URL resolution in `useTemplates.ts` so custom template backgrounds render.
3. **Template preview rendering**: Generate thumbnail previews for custom templates using the same slide render component used for live output. Cache thumbnails in IndexedDB.
4. **Real-time updates**: Subscribe to Convex template changes in studio layout so new templates appear immediately.

### Affected Files

## SPEC-11: Native Media Upload for Desktop Mode

### Problem
The `MediaUpload` component uses a web-based drag-and-drop approach with simulated upload progress. In desktop (Tauri) mode, this should use native file dialogs and native file transfer for better performance, native feel, and larger file handling (videos, high-res images).

### Evidence
- `MediaUpload.tsx` — `handleUpload()` simulates progress with `setTimeout` increments. No actual upload to Convex storage is implemented.
- `fileDialog.ts` — Already has a Tauri-native `openFileDialog()` implementation with `@tauri-apps/plugin-dialog` and `@tauri-apps/plugin-fs`. This is used for file selection but not wired to the upload flow.
- `platform/tauri.ts` and `platform/web.ts` — Platform abstractions exist but upload is not implemented in either.

### Acceptance Criteria
1. In desktop mode, clicking "Upload" opens a native file dialog (already implemented in `fileDialog.ts`).
2. Selected files are uploaded to Convex storage using the `generateUploadUrl` mutation (already referenced in `useTemplates`).
3. Upload progress shows real percentage (not simulated) with cancel support.
4. In web mode, drag-and-drop upload works with the same Convex storage backend.
5. Large files (100MB+) upload without blocking the UI (use chunked upload or streaming).
6. Uploaded media appears in the media library immediately after upload completes.

### Approach
**Decision: Implement both desktop and web upload in v1.**

1. **Wire Convex upload**: In `MediaUpload`, replace the simulated `handleUpload` with a real upload using `convex.storage` — call `generateUploadUrl`, then `fetch(uploadUrl, { body: file })`.
2. **Progress tracking**: Use `XMLHttpRequest` (or `fetch` with `ReadableStream`) to track real upload progress via `onprogress`.
3. **Native file picker**: In desktop mode, use `openFileDialog()` from `fileDialog.ts` instead of the web input element. The returned `File` object flows into the same upload pipeline. Web mode retains drag-and-drop + `<input type="file">`.
4. **Cancel support**: Track `AbortController` per upload. Add a cancel button per file.
5. **Media library integration**: After upload, call a Convex mutation to create a media record with the storage ID, metadata (name, size, type, dimensions).

### Affected Files
- `src/components/media/MediaUpload.tsx`
- `src/utils/fileDialog.ts`
- `convex/media.ts` (new — or extend existing)
- `src/hooks/useMediaLibrary.ts` (new or extend)
- `src/platform/tauri.ts`

## SPEC-12: Template Identification Improvements in Studio Settings

### Problem
Templates in the studio layout settings use colored balls/badges for category identification (blue=announcement, purple=worship, amber=sermon, green=prayer, gray=general). These colors alone make it difficult to identify which template is which without hovering, especially when multiple templates of the same category exist.

### Evidence
- `TemplateBrowser.tsx:78` and `CreateTemplateModal.tsx:32` — Category colors are `bg-blue-500`, `bg-purple-500`, etc.
- Template cards show a gradient placeholder (`from-primary-500/80 to-purple-600/80`) with the template name, but no rendered preview.
- No thumbnail image is generated or stored for custom templates (the `thumbnail` field exists but is empty).

### Acceptance Criteria
1. Template cards show a rendered thumbnail preview (not just a gradient placeholder) for both system and custom templates.
2. Category identification uses both color AND label text (e.g., "Worship" label next to the dot, not just a colored dot).
3. Template name is always visible without hover, even on small cards.
4. In the grid view, template cards have enough contrast between the thumbnail/preview and the overlay text.

### Approach
1. **Rendered thumbnails**: Generate thumbnail previews by rendering a slide with the template's background and style to a small canvas. Store the resulting data URL in the template's `thumbnail` field.
2. **Category labels**: Replace color-only badges with `CategoryDot + CategoryLabel` (e.g., `🟠 Worship`).
3. **Card redesign**: Use a card layout with thumbnail at top, name below, category badge in the corner. Ensure name text has a dark backdrop or is on a light band.
4. **Thumbnail generation**: Create a `generateThumbnail(template): Promise<string>` utility that renders a slide preview to an offscreen canvas and captures it as a PNG data URL. Run this when saving a template.

### Affected Files
- `src/components/templates/TemplateBrowser.tsx`
- `src/components/modals/CreateTemplateModal.tsx`
- `src/components/modals/SaveAsTemplateModal.tsx`
- `src/hooks/useTemplates.ts` (add thumbnail generation)
